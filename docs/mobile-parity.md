# Mobile report parity

The private viewer reads the desktop's saved reports for 1, 7, 30 and 90 days. It does not rescan the phone, reprice reports or force the desktop to refresh. The source timezone and report window travel with the data. [SnapshotBuilder](../internal/sync/snapshot.go) collects the four report types, [the envelope](../internal/sync/envelope.go) compresses and encrypts their JSON, and [mobile validation](../internal/mobile/snapshot_validation.go) checks decrypted candidates before the [viewer transport](../frontend/src/web/snapshotTransport.tsx) answers generated desktop binding calls.

Read-only presentation is established by [mountViewer](../frontend/src/web/mountViewer.tsx). The transport rejects unsupported actions when no host fallback is supplied; Android uses its native host for permitted device actions. This transport is not a universal authorization layer for arbitrary supplied fallbacks. Existing account labels, quota identity/fingerprint fields and source fingerprints (including resolved source paths used for deduplication) remain in private report data. Their preservation is not a claim that all identity/path data has been removed. No new credential or transcript export is added.

## Tested boundary

The single synthetic `reportParityJSON` fixture in [snapshot_test.go](../internal/sync/snapshot_test.go) supplies distinct nonzero business values for every period. Go tests strictly decode its field names against current report types. Mobile and frontend tests extract that raw string as test data; they do not execute Go source. This avoids maintaining separate exhaustive fixtures. Window expansion includes the rolling hourly 1-day view and daily longer views. These are report-preservation tests, not a new statistical calculation benchmark.

- [Builder tests](../internal/sync/snapshot_test.go) compare all supplied reports/settings with the built snapshot and its JSON round trip, and assert that configuration is never requested or serialized.
- [Envelope tests](../internal/sync/envelope_test.go) compare decrypted bytes and typed reports. Seventeen in-memory negative controls strip historical fields/settings or substitute the 30-day report for 7 days; the preservation oracle detects each loss without changing production files.
- [Mobile regressions](../internal/mobile/snapshot_regression_test.go) exercise authenticated relay responses, validation, candidate acknowledgement, encrypted cache and cold-start reads with populated data. Accepted A survives invalid B; recovered C, including 200 Loss rows and larger full-period totals, persists only after acknowledgement. [Validation tests](../internal/mobile/snapshot_validation_test.go) also reject wrong numeric types in nested business fields while retaining legacy/default compatibility.
- [Android interpretation](../frontend/src/android/snapshot.test.tsx) preserves all report/settings data and candidate metadata. [Transport tests](../frontend/src/web/snapshotTransport.test.tsx) call actual generated bindings for all four periods, verify nested conversions and cost/token shares, preserve untimed defaults and complete names, and prove consumer mutations do not alter the source snapshot. They cover device bootstrap overrides, local display changes and unsupported desktop writes.

Targeted Go tests/vet and frontend report/transport tests, type checking, scoped lint and formatting are the local checks for this work. Existing render/save rejection regressions remain applicable. The pre-existing **render failure while cache save is already pending** race is a separate production follow-up: these tests do not claim durable rollback for that case.

The integration acceptance record reuses the accepted T1/T2 screenshots and the T3 browser run of eight scenarios / 37 assertions with controlled host/native mocks. Those checks are not new T4 browser runs. Unit tests cannot establish pixel layout, Android system insets, touch targets, clipboard/chooser behavior or real platform callback delivery. No native device/emulator was available; those paths remain unverified. Native diagnostics boundaries and API-level limitations are documented in [diagnostics.md](diagnostics.md). T4 does not perform bundles, CI, Git operations or release publication.
